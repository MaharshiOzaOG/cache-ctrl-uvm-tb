## 1. Goal & why
- Today memory latency is random in one range for every address, and errors are a random % (plus `force_rd_err`/`force_wr_err` = "fail the next N").
- You can't say "fail exactly the 3rd refill", "fail writebacks to this line", or "addresses below 0x1000 are fast". Error tests depend on luck.
- The memory agent is not reset-aware (the likely source of the U1 test's remaining error).
- After U3: a small policy in `cache_cfg` decides latency / errors / bandwidth deterministically; the memory side survives reset. Empty policy = today's behaviour.

## 2. Understand first

- [ ] **Q1.** Where is the memory's answer decided today, and where is it driven?
<details><summary>✅ Answer</summary>

Decided in `mem_resp_seq::body()` (latency, err, rdata, write into `cfg.mem`). Driven by `mem_drv` (waits the latency, drives `mem_rsp_*`, holds until `mem_rsp_ready`).
</details>
<details><summary>❓ Why change the sequence, not the driver</summary>

Rule "one owner per decision": content and policy live in the sequence, pin timing in the driver. The driver stays generic.
</details>

- [ ] **Q2.** What does "fail the 3rd refill" need the responder to count?
<details><summary>✅ Answer</summary>

A counter of read requests seen (`n_rd_seen`), incremented for every refill. When it equals the rule's `nth`, set `err = 1`.
</details>

- [ ] **Q3.** At a mid-test reset, which memory-agent pieces can hold stale state?
<details><summary>✅ Answer</summary>

`mem_drv` (an answer it is holding / waiting to drive), `mem_mon` (`pend_q` entries), and `dut_req_fifo` in `mem_seqr` (requests not yet answered by the responder).
</details>

- [ ] **Q4.** Why must `mem_drv` call `item_done()` for an item it was holding at reset?
<details><summary>✅ Answer</summary>

The responder sequence is blocked in `finish_item()` until `item_done()`. Without it the responder never takes the next request, and memory stops answering after reset.
</details>

## 3. Implementation checklist

**A. Policy classes: new `mem_policy.sv`** (include in `cache_tb_pkg.sv` **before** `mem_resp_seq.sv`)
- [ ] `mem_region`: `addr_lo`, `addr_hi`, `lat_min`, `lat_max`.
- [ ] `mem_err_rule`: `kind` (read/write), `nth` (0 = unused), `addr` + `use_addr`.

**B. Config (`cache_cfg.sv`)**
- [ ] Queue of `mem_region` (empty), queue of `mem_err_rule` (empty).
- [ ] `mem_bw_max` (0 = no limit), `mem_bw_window` (cycles).
- [ ] Print counts in `convert2string()`.

**C. Responder (`mem_resp_seq.sv`)**
- [ ] Counters `n_rd_seen`, `n_wr_seen`.
- [ ] `pick_latency(addr)`: region match → its range; else `mem_lat_min..max`.
- [ ] `pick_error(req)`: any matching rule → 1; else today's `force_*_err`, then random %.
- [ ] `build_rdata(req, err)`: today's data logic.
- [ ] Bandwidth: queue of recent answer times; if `mem_bw_max` reached in the window, add latency.
- [ ] `body()` only calls these in order, then `start_item` / `finish_item`.
<details><summary>✅ Answer (sketch of pick_error)</summary>

```systemverilog
function bit pick_error(mem_item req, int unsigned n_seen);
  foreach (cfg.mem_err_rules[i]) begin
    mem_err_rule r = cfg.mem_err_rules[i];
    if (r.kind == req.we && ((r.nth != 0 && r.nth == n_seen) ||
                             (r.use_addr && r.addr == line_base(req.addr))))
      return 1;
  end
  // fall back to today's behaviour (force_*_err, then random %)
  ...
endfunction
```
</details>

**D. Memory-side reset**
- [ ] `mem_drv.sv`: same pattern as U1 (`forever` / `fork…join_none` / wait reset / `disable fork`), drive `req_ready`, `rsp_valid`, `rsp_err` to 0, `item_done()` the held item (keep it in a member like `cur_req`).
- [ ] `mem_mon.sv`: on reset empty `pend_q`, skip checks.
- [ ] `mem_seqr.sv`: `run_phase` that on every falling `rst_n` calls `dut_req_fifo.flush()`.
<details><summary>❓ Why flush the FIFO</summary>

Requests the cache made before the reset must not be answered after it; the fresh cache never asked for them.
</details>
