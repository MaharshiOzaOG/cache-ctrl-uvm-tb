## 1. Goal & why
- Protocol rules are checked only by SVA today. Without the SVA bind (another DUT, gate-level) a broken handshake goes unnoticed.
- A reset leaves stale entries in `pending[]`, so `check_phase` and later responses report false errors.
- No latency summary at the end.
- After U2: the monitor checks the handshake rules itself, survives reset, prints statistics; the scoreboard forgets unmatched memory traffic on reset.

**Already in `cpu_mon` (don't redo):** unknown response id → error; id reused while in flight → error; no response after `rsp_timeout` cycles → error; `check_phase` checks `pending` is empty.

## 2. Understand first

- [ ] **Q1.** What exactly is the "stable while waiting" rule on the request channel?
<details><summary>✅ Answer</summary>

If on one edge `req_valid = 1` and `req_ready = 0`, then on the next edge `req_valid` must still be 1 and `req_id/we/addr/wdata/wstrb` must be unchanged. Same on the response channel with `rsp_valid/rsp_ready` and `rsp_id/we/rdata/err`.
</details>

- [ ] **Q2.** To check that rule, what does the monitor need to remember from the previous cycle?
<details><summary>✅ Answer</summary>

The previous cycle's `valid`, `ready` and all fields of that channel. Compare this cycle against them, then copy this cycle into the "previous" variables.
</details>

- [ ] **Q3.** Why have the same check in SVA **and** the monitor?
<details><summary>❓ Why</summary>

SVA is bound to this RTL and uses `$error` (not counted by UVM until A1). The monitor check is part of the reusable agent: it works with any DUT that uses this interface, and its errors are UVM errors that fail the test. Duplicated checks also cross-validate each other.
</details>

- [ ] **Q4.** What should the monitor do with `pending[]` when `rst_n` goes low, and why?
<details><summary>✅ Answer</summary>

Count the entries (aborted requests), delete all of `pending[]` and `reported_hang[]`, skip checks while in reset. The DUT forgot those requests, so their answers will never come; keeping them would cause false "never got a response" errors.
</details>

- [ ] **Q5.** Why must the scoreboard clear `mem_hist` on reset?
<details><summary>✅ Answer</summary>

A refill/writeback that was in flight when the cache was reset belongs to no CPU access anymore. Left in `mem_hist`, the next CPU access would see it outside its time window and report "memory transaction outside any CPU access".
</details>

## 3. Implementation checklist

**A. Config (`cache_cfg.sv`)**
- [ ] Add 1-bit knob `mon_checks_en`, default 1.

**B. Request stability check (`cpu_mon.sv`)**
- [ ] Members for last cycle's `req_valid, req_ready, req_id, req_we, req_addr, req_wdata, req_wstrb`.
- [ ] Each cycle (if `mon_checks_en`): if last cycle had `valid=1, ready=0`, this cycle `valid` must be 1 and fields equal → else `` `uvm_error("CPU_MON_PROTO", ...) `` with both values.
- [ ] At the end of each cycle, copy this cycle's pins into the "last" members.
<details><summary>✅ Answer (sketch)</summary>

```systemverilog
if (cfg.mon_checks_en && p_req_valid && !p_req_ready) begin
  if (vif.mon_cb.req_valid !== 1'b1 ||
      vif.mon_cb.req_addr  !== p_req_addr || vif.mon_cb.req_id !== p_req_id || ...)
    `uvm_error("CPU_MON_PROTO", $sformatf("request changed while waiting: addr %h -> %h", p_req_addr, vif.mon_cb.req_addr))
end
p_req_valid = vif.mon_cb.req_valid; p_req_ready = vif.mon_cb.req_ready; p_req_addr = vif.mon_cb.req_addr; ...
```
</details>

**C. Response stability check (`cpu_mon.sv`)**
- [ ] Same for `rsp_valid, rsp_ready, rsp_id, rsp_we, rsp_rdata, rsp_err`.

**D. Reset handling (`cpu_mon.sv`)**
- [ ] Replace the one-time reset wait with a per-cycle check of `rst_n`.
- [ ] While `rst_n = 0`: `n_aborted += pending.num()`, delete `pending[]` and `reported_hang[]`, clear the "last" members, skip all checks.
<details><summary>❓ Why clear the "last" members</summary>

Otherwise the first cycle after reset compares against a request from before the reset and reports a false "changed while waiting".
</details>

**E. Statistics (`cpu_mon.sv`)**
- [ ] Counters: completed accesses, sum/min/max `lat_cycles`, protocol errors, `n_aborted`.
- [ ] Update at each response handshake.
- [ ] `report_phase`: one `uvm_info` line with count, min, max, average, protocol errors, aborted.

**F. Scoreboard reset (`cache_scoreboard.sv`)**
- [ ] Add a `run_phase`: forever wait for `rst_n` to fall (vif via `cfg.cpu_vif`), then `mem_hist.delete()`.
<details><summary>💡 Hint</summary>

`forever begin @(negedge cfg.cpu_vif.rst_n); mem_hist.delete(); end`. The scoreboard has `cfg` already.
</details>

**G. Prove the checks can fail**
- [ ] Temporarily make the CPU driver change `req_addr` while waiting (cfg knob, story D3). Expected: SVA `ENV:` message **and** `CPU_MON_PROTO`. Undo after.

**H. Regression**
- [ ] Smoke, directed, rand pass and print the statistics line.
- [ ] `cache_reset_test`: no `CPU_MON` errors any more (memory-side errors may remain until U3).
