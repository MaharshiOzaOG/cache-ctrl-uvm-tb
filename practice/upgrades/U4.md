## 1. Goal & why
- The hardest flush case: **a flush arrives while a CPU request is waiting**. Today `cache_flush_race_vseq` fires flushes at random times and hopes to hit it; single runs reached only 83% flush coverage.
- After U4: the flush driver can wait for that exact moment and start the flush then, every time (coverage-driven stimulus).

## 2. Understand first

- [ ] **Q1.** What does "a CPU request is waiting" look like on the pins?
<details><summary>✅ Answer</summary>

`req_valid = 1` and `req_ready = 0` on the same edge (the cache is busy with a miss or a flush).
</details>

- [ ] **Q2.** If `flush_req` and a CPU request are both pending when the cache returns to IDLE, which wins?
<details><summary>✅ Answer</summary>

The flush. `req_ready = (state == IDLE) && !flush_req`, so the cache refuses the CPU request while `flush_req` is high and starts the flush first.
</details>

- [ ] **Q3.** Who can see "CPU request waiting", and who needs to know it?
<details><summary>✅ Answer</summary>

`cpu_mon` sees it (it samples the CPU pins). `flush_drv` needs it (to raise `flush_req` at that moment).
</details>

- [ ] **Q4.** How do two components share an event without being connected by ports?
<details><summary>💡 Hint</summary>

Both already hold the same `cfg` object.
</details>
<details><summary>✅ Answer</summary>

Put a `uvm_event` handle in `cache_cfg` (created in its constructor). `cpu_mon` calls `trigger()`, `flush_drv` calls `wait_trigger()`.
</details>
<details><summary>❓ Alternative</summary>

`flush_drv` uses `cfg.cpu_vif` already, so it could read `req_valid/req_ready` itself. The event version is cleaner (the monitor owns "observing") and teaches component synchronisation.
</details>

- [ ] **Q5.** What happens if no CPU request ever waits while a `TRIG_ON_CPU_WAIT` flush is pending?
<details><summary>✅ Answer</summary>

The flush driver would wait forever. Add a safety limit (e.g. `cfg.rsp_timeout` cycles), then warn and raise the flush anyway.
</details>

## 3. Implementation checklist

**A. Trigger type (`cache_tb_defs.sv`)**
- [ ] `typedef enum {TRIG_NOW, TRIG_DELAY, TRIG_ON_CPU_WAIT} flush_trig_e;`

**B. Item (`flush_item.sv`)**
- [ ] Fields `trigger` (default `TRIG_NOW`) and `delay` (default 0), not `rand`. Add to `convert2string()`.

**C. Shared event (`cache_cfg.sv`)**
- [ ] `uvm_event cpu_wait_ev;` created in the constructor.

**D. Raise it (`cpu_mon.sv`)**
- [ ] Every cycle with `req_valid = 1 && req_ready = 0`: `cfg.cpu_wait_ev.trigger()`.

**E. Wait for it (`flush_drv.sv`)**, before raising `flush_req`:
- [ ] `TRIG_NOW`: as today.
- [ ] `TRIG_DELAY`: wait `delay` edges.
- [ ] `TRIG_ON_CPU_WAIT`: `wait_trigger()`, then raise on the next edge.
- [ ] Safety limit: after `cfg.rsp_timeout` cycles without the event, `uvm_warning` and raise anyway.
<details><summary>✅ Answer (sketch)</summary>

```systemverilog
case (req.trigger)
  TRIG_DELAY:       repeat (req.delay) @(vif.flush_cb);
  TRIG_ON_CPU_WAIT: fork
                      cfg.cpu_wait_ev.wait_trigger();
                      begin repeat (cfg.rsp_timeout) @(vif.flush_cb);
                            `uvm_warning("FLUSH_DRV", "no CPU wait seen, flushing anyway") end
                    join_any
                    disable fork;
  default: ;
endcase
@(vif.flush_cb);
vif.flush_cb.flush_req <= 1'b1; ...
```
</details>
