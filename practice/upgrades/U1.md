## 1. Goal & why
- Before U1, the driver waited for reset only once. A reset in the middle of a test wipes the DUT, but the driver kept waiting for answers that never come, and the sequence hung in `get_response()`.
- After U1: on reset the driver drops its outputs, returns every unfinished request to its sequence with `aborted = 1`, clears its state, and restarts with fresh handshakes.

## 2. Understand first

- [ ] **Q1.** Which handshake signals does the CPU driver own, and which does the DUT own?
<details><summary>✅ Answer</summary>

Driver: `req_valid` (+ request fields) and `rsp_ready`. DUT: `req_ready` and `rsp_valid` (+ response fields).
</details>
<details><summary>❓ Why it matters</summary>

On reset the driver can only control its own outputs, so `reset_state()` drives `req_valid` and `rsp_ready` to 0. `req_ready` / `rsp_valid` come from the RTL (`cache_ctrl.sv` lines ~719/721) and follow the DUT's reset.
</details>

- [ ] **Q2.** At reset, where can an unfinished request be? Name both places.
<details><summary>💡 Hint</summary>

One is "accepted by the cache, waiting for its answer". The other is "taken from the sequence with `get()`, not yet accepted".
</details>
<details><summary>✅ Answer</summary>

1. In `inflight[]` (accepted, waiting for the answer).
2. In `cur_req` (got from the sequence, waiting at the free-slot loop, the gap, or the `req_ready` loop).
</details>

- [ ] **Q3.** Why `put()` aborted items back instead of just deleting them?
<details><summary>✅ Answer</summary>

Each item's sequence is blocked in `get_response()` until someone `put()`s that item. Deleting it would leave the sequence (and the whole test) waiting forever.
</details>

- [ ] **Q4.** Why `join_none` + `disable fork` instead of checking `rst_n` inside the threads?
<details><summary>✅ Answer</summary>

The threads wait in many places (`get()`, slot loop, `req_ready` loop, response edge). Checking reset in each would be easy to miss. `disable fork` from `run_phase` stops them wherever they are, in one place. `join_none` lets `run_phase` continue to the reset wait while the threads run.
</details>

- [ ] **Q5.** Why does `run_phase` need a `forever` loop?
<details><summary>✅ Answer</summary>

Without it, after the first reset `run_phase` ends and no threads restart, so new requests are never driven. The loop restarts the threads when reset ends and handles any number of resets.
</details>

- [ ] **Q6.** Why does the reset test fork the traffic and the reset, with `wait_cycles` first?
<details><summary>✅ Answer</summary>

`rand_ops()` returns only after every answer arrived, so a reset after it hits an idle cache: 0 requests aborted, U1 code never runs. Forking puts the reset **during** traffic; `wait_cycles(random)` makes it land in the middle, at a different spot each run.
</details>

- [ ] **Q7.** Why flush and switch to loads only (`store_pct = 0`) before the reset?
<details><summary>✅ Answer</summary>

Reset throws away dirty lines. The reference model does not know that, so later loads would show false mismatches. Flushing first puts all data in memory; loads only means no new dirty data during the reset window.
</details>

## 3. Implementation checklist

- [x] **A.** `cpu_item.sv`: plain field `aborted`, default 0.
<details><summary>✅ Answer</summary>

`bit aborted = 0;`. Not `rand`, so `randomize()` never touches it. Optional: print it in `convert2string()`.
</details>

- [x] **B.** `cpu_drv.sv`: member `cur_req`; set right after `get(req)`; set to `null` right after `inflight[req.id] = req`.
<details><summary>❓ Why null at accept</summary>

From the accept edge the item is tracked by `inflight[]`. If `cur_req` still pointed to it, a reset would `put()` it twice (UVM response-queue error). `null` = "nothing waiting to be accepted".
</details>

- [x] **C.** `reset_state()` task: drive `req_valid`/`rsp_ready` to 0; loop over `inflight[]`, set `aborted`, `put()`; delete all after the loop; same for `cur_req` if not null; clear `outstanding`, `next_id`; print count.
<details><summary>✅ Answer (sketch)</summary>

```systemverilog
task reset_state();
  int unsigned n = 0;
  vif.drv_cb.req_valid <= 0;
  vif.drv_cb.rsp_ready <= 0;
  foreach (inflight[i]) begin inflight[i].aborted = 1; seq_item_port.put(inflight[i]); n++; end
  inflight.delete();
  if (cur_req != null) begin cur_req.aborted = 1; seq_item_port.put(cur_req); cur_req = null; n++; end
  outstanding = 0; next_id = 0;
  `uvm_info("CPU_DRV", $sformatf("reset: %0d request(s) aborted", n), UVM_MEDIUM)
endtask
```
</details>
<details><summary>❓ Why delete after the loop</summary>

Deleting entries of an associative array while `foreach` walks it is simulator-dependent; an entry can be skipped and never returned.
</details>

- [x] **D.** `run_phase`: `forever { wait rst_n=1; fork request_thread; response_thread; join_none; wait rst_n=0; disable fork; reset_state(); }`
- [x] **E.** `cpu_seq_lib.sv` `do_op()`: if `rsp.aborted`, print "aborted by reset".
- [x] **F.** Reset trigger: `tb_reset_req` in `cache_cpu_if`; `always @(posedge cpu_if.tb_reset_req)` in `tb_top` pulses `rst_n` 5 cycles; `pulse_reset()` in `cache_base_vseq`.
<details><summary>❓ Why release on a falling edge</summary>

Same as the start-up reset: `rst_n` never changes at the rising edge where the DUT's flops sample, so there is no race.
</details>

- [x] **G.** `cache_reset_vseq` + `cache_reset_test`, registered in `cache_tb_pkg.sv`.
- [x] Cleanup: second `n++` inside `if (cur_req != null)`; `timeout_thread` and `cpu_rsp_timeout` removed.
- [ ] Optional: add an **idle** reset step (`pulse_reset()` after `rand_ops`, before the fork) so both cases are covered.
- [ ] Regression: `cache_smoke_test`, `cache_directed_test`, `cache_rand_test` still pass.
